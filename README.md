## 它能做什么

小米官方提供五个下载地址。它们看起来是等价的，实际表现差别很大。mirom 会把这五个地址全部展开、逐个探测、自动选择，然后并行下载。

已知的一个反常情况是：其中两个地址会返回完全正常的 `206` 响应、完整的 `Content-Length`，但每秒只传输一个 16 KB 的数据包，并且一直持续下去。常规下载工具会把它当作可用线路，然后在 0% 处长时间没有进展。这一条在后面的「这些结论是怎么来的」里展开。

实测记录（千兆网络，单机测试）：

| 机型 | 大小 | 耗时 | 平均速度 |
|---|---|---|---|
| marble（Redmi Note 12 Turbo） | 6.898 GB | 1:39 | 71 MB/s |
| renoir（小米 11 Lite 5G NE） | 5.795 GB | 1:30 | 65 MB/s |
| pipa（Xiaomi Pad 6） | 4.713 GB | 1:39 | 48 MB/s |
| davinci（Redmi K20） | 2.380 GB | 0:42 | 57 MB/s |
| lime（Redmi 9 印度版） | 3.637 GB | 0:51 | 72 MB/s |

全部通过文件名内嵌的 MD5 前缀校验。这些数字来自单一测试环境，换网络、换时段会有出入。

## 使用

### 运行

解压后双击 `mirom.exe`。免安装，不需要预先装 Python。

整个文件夹需要一起保留，单独拷走 `mirom.exe` 无法运行 —— 同级的 `_internal` 目录里是运行库。

### 下载

将小米 ROM 的下载链接填入顶部输入框，形如 `https://bigota.d.miui.com/.../xxx.zip`，点击「开始下载」。完成后文件位于 `C:\Users\<用户名>\Downloads\Roms`。

首次使用可以先点「仅测速」。该模式只探测各线路速率，不向磁盘写入任何内容，适合用来确认当前网络下哪条线路最优。

### 设置

快捷键 `Ctrl+,`。以下参数此前仅能通过命令行指定：

| 项目 | 说明 |
|---|---|
| 下载目录 | 输出位置 |
| 并发连接数 | `0` 表示自动调优。手动填写将跳过并发爬坡阶段 |
| 自动调优上限 | 自动调优允许达到的最大连接数，默认 256 |
| 限速 | `0` 表示不限。限制对象是总带宽，所有连接共享同一配额 |
| HTTP 代理 | 留空即不使用 |
| 多线路聚合 | 同时使用多条线路 |
| 完成后校验 MD5 | 建议保持启用。这是判断文件是否完整的唯一手段 |
| 预分配磁盘空间 | 避免边下载边产生碎片 |
| 每次重新调优 | 默认复用 24 小时内的测速结果 |
| 跳过证书校验 | 仅在中间人代理环境下需要 |

关于「多线路聚合」的实际收益：它取决于各线路之间的差异程度。在我测试的环境里提升并不稳定，也没有系统地对比过，因此无法给出可靠的结论。

### 界面

```
┌─ 线路标签 ────────────────────────────────────────┐
│  绿 = 首选   橙 = 较快   灰 = 已排除               │
│  出现「已自动跳过 N 个节点」表示过滤已生效          │
└──────────────────────────────────────────────────┘

┌─ 折线图 ──────────────────────────────────────────┐
│  蓝线 = 总速度   青线 = 单条线路   虚线 = 均值      │
│  黄色标记 = 事件（换线、追加连接等）                │
│  右上角切换 30秒 / 60秒 / 2分钟 / 全程             │
└──────────────────────────────────────────────────┘

┌─ 阶段条 ──────────────────────────────────────────┐
│  探测节点 → 并发调优 → 下载 → 完整性校验            │

└──────────────────────────────────────────────────┘
```

阶段条的第二项容易被误认为卡住。它确实要花几十秒，这期间程序在逐档建立连接并测量吞吐，界面上的速度曲线不会有明显变化。

### 暂停与取消

| 操作 | 行为 |
|---|---|
| 暂停 | 粒度约为总量的 4~5%。已在传输的分片会写完再停 |
| 取消（探测或调优阶段） | 数秒内停止 |
| 取消（下载阶段） | 约 6 秒完成收尾 |
| 取消（校验阶段） | 不可中断，需等待读完整个文件 |

暂停之所以有粒度，是因为分片必须整块落盘才能计入进度。这一点和续传的判定方式有关，后面会再提到。

### 断点续传

中断后重新启动，再次点击「开始下载」即可继续。

进度记录在同目录的 `<文件名>.mirom.json` 中。下载完成并通过校验后，该文件会被自动删除 —— 这是预期行为，不是异常。若再次下载同一个文件，程序会直接跳过。

具体判定逻辑见「续传的判定依据」一节。

### 同名文件

点击「开始下载」时若目标文件已存在，会先弹出对话框：

| 选项 | 行为 |
|---|---|
| 下载副本 | 保留原文件，另存为 `xxx (1).zip` |
| 覆盖重下 | 删除旧文件后重新下载 |
| 跳过 | 不下载，仅校验现有文件 |
| 取消 | 不做任何操作 |

序号被占用时会自动递增。程序不会覆盖任何已存在的文件。

例外情况：如果该文件带有 `.mirom.json` 断点文件，说明上次未完成，此时不会弹窗，直接继续。

### 工具

- **运行引擎自检** —— 弹出结果窗口，同时将逐项结果写入运行日志
- **导出测试数据 CSV** —— 仅测速后即可导出，无需等待下载完成
- **诊断报告** —— 将环境信息与自检结果写入文件，便于反馈问题

导出的 CSV 包含五组数据：

```
① 节点探测      各节点的 TTFB、服务器、可用性、被限速节点的实测速率
② 单连接基准    用于判断是否存在单连接限速
③ 并发爬坡      每一档连接数对应的吞吐与抖动
④ 下载实时速度  仅在执行过下载时存在
⑤ 关键事件      换线、重排等事件发生的时刻
```

### 快捷方式与开机自启

位于「设置」菜单：

- **创建桌面快捷方式**
- **开机自动启动** —— 默认关闭。菜单中的勾选状态读取系统实际状态，手动删除启动项后会同步显示为未勾选

## 常见问题

**速度波动较大**

线路本身存在约两倍的波动。同一份代码、同一个文件，实测耗时可能是 1 分 39 秒，也可能是 3 分 19 秒。程序会自动调整并发并切换线路，建议参考「平均速度」而非瞬时值。

至于这个两倍波动的来源，我倾向认为是 CDN 侧的调度策略，但没有抓到确凿证据，可能有更准确的解释。

**进度停在 0%**

通常是手动指定了被限速的节点。移除链接中指定的节点，让程序自行选择线路。

**进度显示 100% 但未结束**

进度依据的是已完整落盘、可用于续传的单元数，不会提前到达 100%。出现该现象说明正在进行最后的完整性校验 —— 需要完整读取一遍文件计算 MD5，大文件耗时数秒到十几秒。

**提示完整性校验失败**

文件在传输过程中损坏。重新执行同一条命令即可，程序会检测到校验不通过并重新下载整份文件。

**点击按钮时闪过一个黑色窗口**

旧版本存在此现象，现已消除。程序需要查询磁盘类型，旧实现会启动一个 PowerShell 子进程；而打包后的程序本身没有控制台，Windows 会为子进程新建一个窗口。当前所有子进程调用均带隐藏标志，且同一磁盘只查询一次。

**提示输出路径过长**

Windows 默认路径长度上限为 260 字符。请将下载目录移动到层级更浅的位置。

**杀毒软件报警**

这是 PyInstaller 打包程序的常见误报，源码完全公开可自行审查。

## 内部实现

以下记录为什么这样写。所有数值均来自实测，但结论的适用范围仅限于测试过的环境。

### 共享分片队列

直观的做法是把文件切成 N 份、每条连接负责一份。问题在于快线路的线程很快完成任务后无事可做，而慢线路还在处理自己的那份。

这里采用的是一份共享队列：所有连接从同一个队列领取分片，完成后继续领取。分片大小按剩余量和连接数动态计算，保证分片数量至少是连接数的两倍，避免出现分片不够、连接空转的情况。

分片也不低于 2 MB。早期尝试过更细的分片，结果触发了 CDN 的请求频率限制，吞吐从 96 MB/s 掉到 3 MB/s。这个阈值是我反复试出来的，理论上应该存在更优的取值，但没有继续深究。

### 尾部处理

进度超过 90% 后，队列通常已经空了，剩余工作全部由在途连接持有。此时新增的备用线路连接拿不到任务，只能空转退出。

处理方式是把在途分片中最大的若干个截断，剩余部分放回队列，再由备用线路领取。

> 这一机制最初的设计是让所有在途连接交出手上的分片。结果是单次产生 230 多个碎片，四轮重排累计近千个新请求，直接触发限流：吞吐归零，重试次数涨到 144 次。因此现在只处理最大的若干份。

### 进度的计算依据

这是一个不太容易察觉的问题。

写入计数器每写一个字节就加一，而完整性的位图只在整块分片下载完成后才标记。两者在传输过程中必然存在差值。实测差值最大达到 485.5 MB，占 2.38 GB 文件的 20%。

用写入量计算进度会带来两个后果：进度最多虚高 20%；更严重的是写入量可能超过文件大小，经 `min()` 截断后，进度条会在文件还差 22 MB 时显示 `100.00%`，并长时间停滞。

修改方式是把位图改为按 1 MB 单元增量标记，不再等待整块分片完成。差值随后降至 42 MB，约占 1.7%，正好等于所有在途连接各自持有的半个单元之和，已经接近理论下限。

设置环境变量 `MIROM_DEBUG_ACCT=1` 可以实时观察这项指标：

```
[记账] written 909.0 MB | 位图(权威) 874.0 MB | 虚高 35.0 MB | 超出文件大小 0.0 MB
```

### 续传的判定依据

取消后的数据文件是预先分配过的，大小与完整文件完全一致。因此「文件存在且大小相符」无法区分「已完成」和「下载了一半」。

还有一种更隐蔽的情况：校验通过后如果保留断点文件，位图是全满的。文件后续被修改，再次运行时 `load_state()` 会恢复出「全部已完成」，一个分片都不会下载，最后仍然报校验失败 —— 反复重跑都无法修复。

现在的逻辑是：

```
存在断点文件  → 属于续传，交由 load_state() 恢复
不存在断点文件 → 可能是上次已完成，值得完整校验一次
校验通过后    → 删除断点文件
```

删除断点文件之后，再次运行会走「检测到同名文件 → 校验 → 通过则跳过，不通过则重新下载」这条路径，两种情况都能正确处理。

这也是前面提到暂停存在粒度的原因：分片必须整块落盘才计入进度，否则续传时会在文件中留下无法检测的空洞。

### 取消需要是线程级的

探测节点与单连接基准测速这两个阶段合计超过 40 秒，而它们都发生在下载器实例创建之前。

如果取消操作只作用于下载器的停止标志，这 40 秒内点击取消不会产生任何效果，而界面仍会显示「已请求取消」。

现在的做法是增加一个线程级的取消标志，在阶段边界、并发调优内部和节点检测内部都可以查询到。

| 取消时刻 | 修改前 | 修改后 |
|---|---|---|
| 5 秒（探测阶段） | 无响应 | 0.0 秒 |
| 12 秒（探测阶段） | 无响应 | 2.3 秒 |
| 20 秒（测速阶段） | 无响应 | 0.1 秒 |
| 45 秒（下载阶段） | 6.2 秒 | 2.2 秒 |

### 磁盘类型判断

程序会先识别目标介质类型，再决定并发上限：

| 介质 | 并发上限 | 说明 |
|---|---|---|
| 固态盘 | 256 | 按网络状况调优 |
| 机械盘 | 192 | 实测大块并发散写不存在性能问题 |
| 网络盘 | 8 | 每次写入都有网络往返 |
| 可移动介质 | 16 | 带宽有限 |

机械盘之所以不降低并发，依据是以下测试（512 KB 块，全部执行 `fsync`）：

```
机械盘 (WDC WD10EZEX)   顺序写 175.7 MB/s
                        1/16/64/192 线程并发散块写 = 179.4 / 180.3 / 178.9 / 178.0 MB/s
固态盘 (Samsung 980PRO) 顺序写 1554.9 MB/s
                        16~64 线程最佳 (2390/2288)，192 线程回落至 1081 MB/s
```

这组数据只覆盖了两块盘，样本很少，我对其普适性没有把握，仅供参考。

磁盘类型的查询通过 Windows 的 `Get-PhysicalDisk` 完成。打包后的程序没有控制台，需要为子进程显式隐藏窗口，否则会出现一闪而过的黑框。同一磁盘的结果会缓存，不重复查询。

### 正确性保障

这类工具的问题通常不是无法运行，而是运行成功但产出文件已损坏，且不易察觉。因此内置三层检查，可通过 `python mirom.py --selftest` 随时运行。

**静态检查 —— 未定义名称**

使用标准库 `symtable` 扫描引用了但未定义的名称。`compile()` 无法发现这类问题，它只检查语法；而实际触发位置往往在取消、异常处理这类很少执行的分支中。

该检查在开发过程中发现过四次真实缺陷：两次是重命名时遗漏调用点，两次是缺少导入。

**记账不变式 —— 进度不得虚高**

具体见「进度的计算依据」。

**完整性闸门 —— 位图与 MD5**

下载结束后先逐单元确认位图无空洞，再与文件名内嵌的 MD5 前缀比对。

## 这些结论是怎么来的

前面多处提到了一些反常现象，这一节说明它们的来源。

### 五个节点的实际差异

| 节点 | 实际情况 |
|---|---|
| `cdnorg` | 稳定，多数情况下的首选 |
| `aliyun` | 单连接速度快，但抖动明显，尾部可能突然下降 |
| `bn` | 表现不稳定 |
| `bigota` | 见下 |
| `hugeota` | 同 `bigota` |

### 关于 bigota 与 hugeota

这是整个项目中最关键的一个观察。

这两个地址返回完整的 `206` 状态码和 `Content-Length`，从响应头看不出任何异常。但实际传输速率约为每秒 16 KB，并且持续不断：

```
0.00s +16384 累计  16KB     4.00s +16384 累计  96KB
1.00s +16384 累计  32KB     8.00s +16384 累计 176KB
2.00s +16384 累计  48KB    12.00s +16384 累计 256KB
```

这个区别决定了检测方式：由于数据一直在到达，socket 超时不会触发，靠设置超时无法拦截。而按 256 KB 读取会一直阻塞到凑满为止，约需 12 秒，超过了 8 秒的检测预算。

现在改为按 32 KB 小块读取，每次根据剩余预算设置超时，使检测上限真正生效。单节点检测耗时从 12.15 秒降至 8.29 秒，报出的是实测速率而非固定文案：

```
bigota  ✗ 不可用  限速 20 KB/s (8 秒只收到 160 KB, 无法使用)
```

需要说明的是，我把它描述为「限速」而不是「故障」，依据只是传输速率恒定且持续这一点。服务端的具体行为我不了解，这个判断未必准确。

### 并发数存在拐点

单连接速率实测：

```
cdnorg   1.12 MB/s
bn       1.25 MB/s
aliyun  20.12 MB/s
```

因此提高并发是主要手段。但并发并非越高越好：

```
 64 连接 →   79.46 MB/s | 抖动 CV 53.2%
128 连接 →   89.84 MB/s | 抖动 CV 58.3%
192 连接 →   90.30 MB/s | 抖动 CV 54.2%
```

超过 192 之后增益很小，抖动反而上升。程序会自动搜索这个拐点，并按以下准则选择线路：

- 吞吐高出 15% 以上 —— 接受抖动
- 吞吐差距在 ±15% 以内，但抖动低于对方 3/4 —— 选择更稳定的

实际意义在于：`aliyun` 通常比 `cdnorg` 快 5% 到 8%，但抖动是后者的两到三倍，且尾部可能突然下降。这类「看起来更快」的线路不适合作为主线路。

抖动指标使用变异系数衡量。这个指标在连接数较少时参考价值有限，也不是所有网络环境下都适用。

### 其他开发过程中发现的问题

**重定向输出时不能假定存在终端**

当 `sys.stdout` 为 `None` 时，`print()` 是静默的空操作，但显式调用 `.isatty()` 或 `.write()` 会直接抛出异常。打包后的程序正是这种环境。

**同名文件不应静默跳过**

引擎若发现同名文件且 MD5 通过就直接返回成功，用户会认为程序没有正确工作。现在会弹出对话框提供明确选项。

**带查询串的链接会生成非法文件名**

`...zip?token=ABC` 中的 `?` 在 Windows 上是非法字符，会导致打开文件失败；同时内嵌 MD5 也无法提取，因为正则要求以 `.zip` 结尾，结果是静默跳过校验。现在请求路径保留查询串，本地文件名去除。

**配置文件属于用户可见范围**

调优缓存中只要有一个字段类型不正确，就会在探测结束、调优刚开始时崩溃，而此时用户已经等待了约 25 秒。界面菜单中又提供了「打开调优缓存」入口。现在逐字段校验，无效条目直接丢弃。

### 从源码运行

```bash
pip install -r requirements.txt
python mirom_gui.py
```

仅使用命令行时不需要安装任何依赖，`mirom.py` 只使用标准库。

### 打包

双击 `tools\打包.bat`，需要 Python 3.8 或更高版本。

打包逻辑只保留一份，即 `tools/build.py`，本地与持续集成均调用它。如果将那一长串模块排除参数在两处各写一遍，某次只修改其中一处，两边的产物就会出现差异。

```bash
python tools/build.py              # 完整打包
python tools/build.py --zip        # 打包并生成压缩包
python tools/build.py --skip-logo  # 跳过图标生成
```

### 测试

```bash
python mirom.py --selftest          # 引擎自检
python tests/test_edge.py           # 边界条件，不需要网络
python tests/test_settings.py       # 界面与设置，不需要网络
python tests/test_gui_buttons.py    # 界面遍历，需要网络
```

### 持续集成

仓库包含 GitHub Actions 工作流，无需 Windows 环境也能获得可执行文件：

- 推送到 `main` —— 运行测试与打包，产物位于 Actions 页面的 Artifacts 中
- 推送 `v*` 标签 —— 额外创建 Release 并附上压缩包
- 手动触发 —— 在 Actions 页面选择 Run workflow

工作流在构建之后会再次校验产物本身：可执行文件的属性信息、内嵌图标的帧数、资源目录中是否存在空文件。仅确认构建无报错是不够的。
